執行以下步驟，為指定作業產生**操作手冊**與**測試項目**，並產出院方格式之 Word 交付文件。

## 參數說明（$ARGUMENTS）

| 參數 | 必選 | 說明 | 範例 |
|------|------|------|------|
| `<作業代碼>` | 必填 | 作業代碼（如 `bs03`、`ma01`），不分大小寫 | `/sti-manual bs03` |
| `test` | 選填 | 只補測試項目，不動手冊 | `/sti-manual bs03 test` |
| `image` | 選填 | 圖已備妥，只接圖並重新產出 | `/sti-manual bs03 image` |

---

## 執行步驟

### 步驟 0：載入規範（不可略過）

依序讀取下列三檔，後續一切依其規定辦理；**本指令不重述其內容，以免兩份漂移**：

1. `docs/manuals/README.md` —— 作業步驟總覽
2. `docs/manuals/手冊撰寫規範.md` —— 章節骨架、寫作判準、用語、禁止事項
3. `docs/manuals/截圖作業指引.md` —— 待拍清單格式與通用畫面清單

### 步驟 1：解析參數並定位素材

1. 作業代碼正規化為大寫（`bs03` → `BS03`），前兩碼為模組碼
   （`BS`／`MA`／`CP`／`DP`／`LB`／`MC`／`TL`／`BC`）
2. 自規範〈用語規範〉之作業名稱對照表取得**正式作業名稱**，⛔ 不自行命名
3. 對照 `docs/specs/{模組}/spec.md` 之 US 對照表，找出該作業碼對應之 **US 編號**
   （⚠️ US 編號與作業碼**不一致**，如 BS06 對應 US12），據以定位 `spec_us{N}.md`
4. 若查無該作業碼，列出該模組已知之作業碼供使用者確認後停止

### 步驟 1.2：確認該模組已就緒

第一次處理某模組時，下列資產可能尚未建立，**逐項檢查並補齊**：

| 資產 | 不存在時 |
|---|---|
| `docs/manuals/{模組}/` | 建立 |
| `docs/manuals/_images/{模組}/` | 建立 |
| `docs/manuals/_tests/{模組碼}-{模組名}.md` | 建立，文件標題為模組**正式名稱** |
| `gen_manual.py` 之 `MODULE_NAMES` 有無該模組 | **停下來詢問使用者**，見下 |

**模組正式名稱**指院方交付文件所用之名稱，⛔ **不得以 spec 之內部慣稱替代**
（spec 稱「成分模組」「資訊模組」，院方文件則為「成分作業管理模組」等）。已登錄者：

| 模組碼 | 正式名稱 | 依據 |
|---|---|---|
| BS | 血品庫存管理模組 | 院方需求規格確認書 |
| MA | 醫務作業管理模組 | BS 規格之引用 |
| CP | 成分作業管理模組 | BS 規格之引用 |

未登錄之模組（DP／LB／MC／TL／BC）**MUST 先向使用者確認其對外正式名稱**，取得後
補入 `MODULE_NAMES` 再續行。⛔ **不得自行推定**——該名稱會印在交付文件封面，
錯誤即交付瑕疵。

詢問時**以 AskUserQuestion 提出選項**，並附上判斷依據供使用者挑選或自填：

- 選項一：spec 標題所用之內部名稱（如 DP 之「資訊模組」）——標明**此為內部慣稱，
  院方文件未必相同**
- 選項二：比照已登錄者之構詞（如「資訊作業管理模組」）——標明**為推測，需確認**
- 併同說明：正確來源為院方交付文件或該模組 SA，若一時無法確認，可先產出手冊、
  待名稱確定後補登再重產（封面會少模組名一行，其餘不受影響）

⚠️ 未登錄而逕行產出者，封面將只有作業名、缺模組名一行，且不會報錯。

### 步驟 1.5：盤點現況並**詢問**本次要做什麼

⛔ **本步驟 MUST 停下來詢問，MUST NOT 逕行執行任何撰寫或產出。**

先逐項盤點現況：

| 盤點項 | 看什麼 |
|---|---|
| 手冊 | `docs/manuals/{模組}/{作業碼}-*.md` 是否存在、章節與圖片引用數 |
| 測試項目 | `_tests/{模組碼}-*.md` 是否已有該作業章節、幾項 |
| 圖片 | `_images/{模組}/` 下該作業之圖幾張，對照待拍清單缺哪幾張 |
| 待拍清單 | `_shots/{作業碼}-*.md` 是否存在（存在即表示圖尚未拍齊） |
| Word | docx 是否存在、是否舊於其來源 md |

**呈現現況摘要後，以 AskUserQuestion 詢問**，⛔ 不自行決定範圍逕行執行——現況常與使用者預期不同（圖是否拍齊、md 是否已定案、是否該產出 Word），
猜錯即做出多餘或錯誤之變更。

**現況摘要**應含：手冊與測試項目是否存在、圖幾張已備／共需幾張、Word 是否已產出
及是否舊於 md。

**選項依現況組成**，僅列當下做得到者，例如：

| 現況 | 可提供之選項 |
|---|---|
| 手冊不存在 | 撰寫手冊與測試項目（之後開待拍清單）；或先只寫手冊，待審閱後再寫測試項目 |
| 手冊在、圖未齊 | 開／更新待拍清單；或「圖已拍好，接圖」 |
| 圖已齊、md 未更新 | 接圖並更新 md |
| md 已定案、Word 未產或已過期 | 產出 Word（步驟 10） |
| 全部完成 | 跑一致性檢查；或重新產出 |

每個選項均應說明**會動到哪些檔案**，使用者得據以判斷。

⛔ **手冊不存在時 MUST NOT 提供「只寫測試項目」**——測試項目依**手冊所述行為**撰寫，
手冊未寫則無從核對，只能對規格做；而規格寫的是系統應有之行為、手冊寫的是使用者
實際如何操作，兩者不等價。日後手冊寫成，該批項目仍須逐條回頭重核，等於做兩次。
`test` 參數之前提亦為手冊已存在。

⚠️ **AskUserQuestion 至少需兩個選項，但 ⛔ MUST NOT 為湊足選項而提供會造成返工之
範圍**。合理選項僅一個時，改以「照此範圍執行」與「改用其他範圍」呈現，由使用者
於 Other 自述。

**首次執行（尚無圖）之範圍**：撰寫手冊與測試項目 → 格式檢查 → 開待拍清單 → 回報。

⚠️ **此階段 MUST NOT 產出 Word**——Word 為最終交付物，內容未定案前產出者不完整
（無圖），徒增誤用之風險。產出一律留待圖片備妥、內容定案後為之（步驟 10）。

⚠️ **此時手冊 MUST NOT 寫入任何圖片引用**——引用尚未存在之圖會使檢查工具報錯。
圖片一律待備妥後插入。

⚠️ 缺圖不阻礙測試項目之撰寫（測試項目不需要圖），亦不得以「待補」字樣寫入手冊
交付，或挑用未經確認之舊圖充數。

### 步驟 2：盤點規格

讀取該作業之 `spec_us{N}.md`，擷取：

- 使用情境、適用角色與站點限制
- 各項操作之流程與前後銜接
- 檔末〈系統訊息〉表之**訊息原文**（供〈常見訊息與處置〉章）
- 標註為停用、未啟用或已廢止之功能 —— **一律不寫入手冊**（使用者看不到）

### 步驟 3：確認畫面實際字樣

⚠️ **本步驟不可省略，且不可憑規格推測**。規格不會記載按鈕與欄位的實際文字。

1. 檢視 `docs/manuals/_images/{模組}/` 下是否已有該作業之截圖
2. 有截圖者逐張比對；取用既有截圖前依規範第六節確認為**現行版**
3. **無截圖可對之處全部列出**，於最終回報標明「未經畫面核對」，不得靜默寫入

### 步驟 4：撰寫手冊

於 `docs/manuals/{模組}/{作業碼}-{作業名}.md` 依規範之章節骨架撰寫。取捨依規範
〈寫什麼、不寫什麼〉之判準；用語依〈用語規範〉；禁止事項依該節逐條檢核。

⚠️ **圖尚未備妥者，本步驟只寫文字、不寫圖片引用**（見步驟 1.5）。

### 步驟 5：撰寫測試項目

寫入 `docs/manuals/_tests/{模組碼}-{模組名}.md`。

⚠️ **測試項目為獨立檔案，非自手冊 md 抽取**——手冊寫「怎麼做」、測試項目寫「一句
可判定合格與否的陳述」，文體不同，MUST 由人依手冊所述行為另行撰寫。

- 該檔**已存在**者，追加一節，⛔ 不另開新檔
- 該檔**不存在**者（該模組第一支作業）建立之，文件標題為模組正式名稱

寫完**雙向核對**，兩個方向都要做：

| 方向 | 檢查 |
|---|---|
| 測試項目 → 手冊 | 每項所述行為，手冊有無說明 |
| **手冊 → 測試項目** | **手冊所寫之重要行為，有無漏測** |

> ⚠️ 反向最易漏。曾發生手冊寫了整段處置流程、測試項目完全未涵蓋之情形。

### 步驟 6：格式檢查

```bash
python docs/manuals/tools/check_manual.py
```

有錯誤者修正 md 後重跑，不得帶錯進入後續階段。

⚠️ **本步驟不產出 Word**，產出見步驟 10。

### 步驟 7：開待拍清單

缺圖者於 **`docs/manuals/_shots/{作業碼}-待拍清單.md`** 開出（一支作業一個檔案），
格式依〈截圖作業指引〉第五節，**五項齊備**：登入身分、資料準備、操作步驟、拍攝範圍、
指定檔名。

⛔ **MUST NOT 寫進截圖作業指引**——該檔為長期規範，多人並行各做不同作業時共改一份
必然衝突。清單為暫時性資產，拍完即刪。

⚠️ 清單開頭 MUST 載明**存放路徑**（`docs/manuals/_images/{模組}/`），步驟 8 之回報亦同。

⭐ **資料準備 MUST 盡可能給具體資料**（訂單編號、血袋號碼、放行日期與批次等），
而非「一張已確認的訂單」這類條件敘述——拍攝者到現場才開始找資料是最易卡住之處。
可查詢資料庫者直接查出填入；不可查者於清單附上查詢用 SQL 供代查。

撰寫時一併寫出「做不出該畫面的前提」（例如需特定狀態之資料、需他人同時操作），
否則拍攝者到現場才發現拍不到。

### 步驟 8：回報

向使用者回報下列各項：

1. 產出之檔案路徑（手冊 md／docx、測試項目、測試報告）
2. 手冊章節結構與測試項目數
3. **未經畫面核對之處**（步驟 3 所列）
4. **待拍清單**（步驟 7 所列，直接呈現於對話，供使用者逐張拍攝），**含存放路徑**
5. 雙向核對之結果，含發現之漏測項目

### 步驟 9：詢問是否續行接圖

有待拍清單者，於回報末尾**詢問使用者圖片是否已備妥**，並告知兩種續行方式：

- 現在拍：拍好後於同一對話告知，**逕行執行下方〈image〉之步驟，不需重新下指令**
- 稍後再拍：結束本次執行，日後以 `/sti-manual {作業碼} image` 接續

使用者告知圖已備妥後，**先確認檔案確實存在**（依待拍清單之指定檔名逐一比對），
缺漏者列出並請其補齊，不得逕行假設已拍齊。

⭐ 於同一對話續行之優點：撰寫脈絡尚在，插圖位置與圖說之判斷較準確；且若發現手冊
描述與畫面不符，可即時回頭修正該段落。

### 步驟 10：產出交付文件（⚠️ 僅於使用者明確要求時執行）

⚠️ **撰寫期間只維護 md，不產出 Word**——Word 為最終交付物，各作業陸續完成期間
反覆產出徒增二進位變更、且隨時會被後續修正推翻。待全部作業定版後統一產出交付。

本步驟僅於使用者**明確要求產出**時執行；平時完成步驟 1～9 後即回報結束。

兩支產生器需 `python-docx`。**未安裝時逕行安裝後續行，⛔ 不要求使用者自行處理**
——套件裝在各人機器上、不隨 repo 取得，且未列入專案依賴，故每個人第一次跑都會缺：

```bash
python -c "import docx"        # 失敗即未安裝
pip install python-docx        # 僅於上一行失敗時執行
```

執行時：

```bash
python docs/manuals/tools/check_manual.py
python docs/manuals/tools/gen_manual.py "docs/manuals/{模組}/{作業碼}-{作業名}.md"
python docs/manuals/tools/gen_acceptance_form.py "docs/manuals/_tests/{模組碼}-{模組名}.md"
python docs/manuals/tools/check_consistency.py
```

⚠️ **產出時 MUST 指定本作業之檔案，⛔ MUST NOT 傳入整個 `docs/manuals` 目錄**——
後者會重產全部手冊，而 docx 即使內容未變，其二進位每次產生皆不同（時間戳與內部
識別），使未經修改之交付文件全數顯示為已變更，難以辨識本次真正動到什麼。

ℹ️ 測試報告為一個模組一份，新增作業後**整份重產屬必然**，非多餘變更。

- 產出須印出「內容核對通過」；有缺漏者依其列出之內容修正 md 後重產
- 一致性檢查會攔下產出過期、手冊與測試項目覆蓋不一致、作業名稱四處不符等問題
- 遇 `Permission denied` 為該 Word 檔開啟中，請使用者關閉後重跑

產出後告知使用者檔案路徑，並提醒 Word 首次開啟會自動更新目錄頁碼。

## 子模式

### `test`：只補測試項目

跳過步驟 4，其餘照走。適用於手冊已完成、事後補測試項目。

### `image`：接圖並重新產出

> 本模式亦為步驟 9 之續行內容；於同一對話續行者直接執行下列步驟即可。

1. 確認 `docs/manuals/_images/{模組}/` 下之新圖
2. **逐張檢視圖片內容**，確認與手冊該段文字相符（機器驗不到，MUST 人工判讀）
3. 插入手冊對應段落，圖說依規範〈圖片〉之要求撰寫
4. 自〈目前待拍清單〉移除已完成項目
5. 執行步驟 10 產出交付文件

> ⚠️ 接圖時常發現手冊描述與實際畫面不符（按鈕層級、操作順序），一律以畫面為準
> 修正手冊，並於回報中列出修正之處。
