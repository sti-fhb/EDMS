# 操作手冊與測試報告：作業說明

本目錄產出兩種交付文件，**來源都是 Markdown，Word 一律由程式產生**：

| 交付文件 | 粒度 | 給誰 |
|---|---|---|
| 操作手冊 | 一支作業一份 | 院方第一線操作人員，照著做 |
| 測試報告 | 一個模組一份（內含各作業一張表） | 驗收人員，逐項勾選合格／不合格 |

**不要手改產生出來的 .docx**——下次重新產生就全沒了。所有修改一律改 md。

## 四個階段

```
①  規格 + 畫面      ─→  操作手冊 md       et/ET02-課程建立與編輯.md
②  依手冊所述行為   ─→  測試項目 md       _tests/ET-教育訓練文件管理模組.md
③  缺圖             ─→  待拍清單 ─→ 拍攝 ─→ 接圖回 md
④  內容定案後       ─→  兩份 Word         gen_manual.py／gen_acceptance_form.py
```

> 重要：**Word 留到最後才產。** 它是最終交付物，內容未定案（圖還沒接）就產出的
> 那份不完整，擺在那裡只會被誤當成完成品。前三階段一律只動 md，跑
> `check_manual.py` 驗格式即可。

> 重要：**測試項目是另一個檔案，不是從操作手冊 md 抽出來的。** 它由人**依手冊所述
> 行為另行撰寫**——手冊寫「怎麼做」、測試項目寫「一句可判定合格與否的陳述」，
> 文體不同，程式轉不出來。兩者的對應靠〈二、新增測試項目〉的雙向核對維持。

docx 有納入版控，沒有 Python 環境的人可以直接從 repo 取用；但它是二進位檔、每次重產都會生出新版本，所以**不必每次修改都提交**，定版時再提交。

---

## 最快的做法：用指令

```
/sti-manual et02          產生該作業之手冊與測試項目
/sti-manual et02 test     只補測試項目
/sti-manual et02 image    圖拍好後接圖並重新產出（中斷後續行用）
```

一般情況**只需下第一行**：指令寫完手冊與測試項目、跑過格式檢查後會開出待拍清單，
並詢問圖片是否已備妥；於同一對話回覆拍好即接著插圖、再產出 Word，不必再下指令。
`image` 供中斷後另起對話續行時使用。

指令會自動依本檔與〈手冊撰寫規範〉的流程執行，並在完成後回報未經畫面核對之處與
待拍清單。以下各節說明其所依循的流程，供人工作業或需要理解細節時參考。

---

## 四份文件的分工

| 文件 | 內容 | 什麼時候看 |
|---|---|---|
| **README.md**（本檔） | 怎麼做，完整步驟 | 第一次接手、或忘記流程時 |
| [手冊撰寫規範.md](手冊撰寫規範.md) | 寫什麼、不寫什麼、用語、禁止事項 | 動筆前必讀；寫的過程隨時查 |
| [截圖作業指引.md](截圖作業指引.md) | 怎麼拍圖、待拍清單 | 需要補圖時；拍攝者照著拍 |
| [搬遷指引.md](搬遷指引.md) | 整套流程搬到其他專案怎麼做 | 要在另一個專案用這套時 |

專案專屬的設定（機關名、購案名、模組清單、命名慣例、禁用字樣）集中於
`tools/manual_config.py`，四支工具一律自此讀取。

## 環境

只需要 Python。產生 Word 用的 `python-docx` 由指令在第一次產出時自行安裝，不必先準備。

自行執行產生器（不透過指令）時才需要手動裝一次：

```bash
pip install python-docx
```

> 套件裝在各人的機器上、不隨 repo 取得，也未列入專案依賴，因此每個人第一次跑都會缺。

`docs/manuals/tools/樣式範本.docx` 是 Word 版面的來源（字體、頁碼、目錄設定都繼承自它），
**刪掉就產不出文件**，不要移動或改名。

## 一、新增一支作業的操作手冊

### 步驟 1：蒐集素材

| 素材 | 從哪裡來 |
|---|---|
| 作業的行為與規則 | `docs/specs/{模組}/spec_us{N}.md`（US 編號與作業碼不同，對照見該模組 spec.md） |
| 系統訊息原文 | 同上，檔末〈系統訊息〉表 |
| 畫面實際字樣 | **截圖或實機**，不可憑規格推測 |

> 重要：規格**不會**告訴你按鈕叫什麼，也不會寫按鈕在什麼條件下才能按。ET02 新增課程
> 時「新增教材」／「新增測驗」按下去會先自動存草稿再開視窗，只有看畫面才知道；寫錯會
> 讓使用者以為操作失敗。

### 步驟 2：建立 md

路徑 `docs/manuals/{模組}/{作業碼}-{作業名}.md`，例如 `et/ET02-課程建立與編輯.md`。
作業名取自〈手冊撰寫規範〉第七節的對照表，不要自己取。

### 步驟 3：依骨架寫內容

固定三章，**編號由程式產生，md 裡不要自己寫**：

```markdown
# ET02 課程建立與編輯    ← 封面用，每檔一個

## 作業說明              → 產出為「壹、作業說明」
### 使用情境             → 產出為「一、使用情境」
### 進入路徑

## 操作說明
### 畫面與前置設定
### （依實際作業順序排列各步驟）

## 常見訊息與處置
### 被擋下（動作沒有完成）
### 有警告（動作完成但需判斷）
### 送出後的結果訊息
```

寫的時候反覆問一句：**這件事看畫面看得出來嗎？** 看得出來的不寫（欄位叫什麼、有哪些
按鈕），看不出來的一定要寫（為什麼被擋、這個值哪來的、做了會怎樣）。詳見規範第四節。

### 步驟 4：對截圖核對畫面用語

逐一核對按鈕、欄位、選單、訊息文字。**這步不能省**，機器驗不到。

### 步驟 5：放圖

圖片放 `docs/manuals/_images/{模組}/`，命名 `{作業碼小寫}-{兩位序號}.png`，
例如 `et02-01.png`。引用時**圖說必填**：

```markdown
![新增章節後，該章節下出現「新增教材」與「新增測驗」兩個入口](../_images/et/et02-01.png)
```

**缺圖就另行截圖**：於 `docs/manuals/_shots/{作業碼}-待拍清單.md` 開出待拍清單。
〈截圖作業指引〉第三節有「每支作業要拍哪些畫面」的通用清單可對照，第五節為清單的
撰寫要求，拍攝者照著拍。

手邊若有既有截圖可用，取用前**務必確認是現行版**——查拍攝日期、對照該作業最後一次
畫面異動（規範第六節有判斷步驟）。過期的圖會把已改掉或已停用的功能寫進手冊。

### 步驟 6：檢查

```bash
python docs/manuals/tools/check_manual.py
```

會擋下：圖片路徑不存在、缺圖說、表格欄數不齊、標題跳級或自行編號、殘留圖示符號、
訊息代碼、issue 編號、資料表名稱、測試流程用語。

### 步驟 7：產出並確認

```bash
python docs/manuals/tools/gen_manual.py docs/manuals
```

印出「內容核對通過」才表示 md 的每一段都進了 Word。之後開 Word 看排版：封面、目錄
頁碼（首次開啟會自動更新）、圖片落點、跨頁位置。

## 二、新增測試項目

測試項目**一個模組一個檔**，新增作業時在同一檔追加一節，不要另開新檔：

```markdown
## ET02 課程建立與編輯     ← 追加在 _tests/ET-教育訓練文件管理模組.md

### 測試前準備
| 項目 | 說明 |
|---|---|
| 登入帳號 | … |
| 資料 | 需要哪些狀態的資料才測得出來 |

### 測試項目清單
| 項次 | 測試內容 |
|---|---|
| 1 | 一句可判定合格與否的陳述 |
```

寫法要求：

- 每項寫成「**做什麼 → 系統應如何反應**」，一句 30～60 字
- 項次於**各作業內自 1 起算**，不跨作業連號
- 涵蓋主流程、權限擋下、各類檢核與結果呈現
- 需要特殊條件才測得到的（兩個以上帳號配合、閱課期間已過之課程、重考次數已用盡之學員），一定要寫進「測試前準備」

產出：

```bash
python docs/manuals/tools/gen_acceptance_form.py
```

### 寫完務必雙向核對

| 方向 | 檢查什麼 |
|---|---|
| 測試項目 → 手冊 | 每一項所述行為，手冊有沒有講到 |
| **手冊 → 測試項目** | **手冊寫的重要行為，有沒有漏測** |

> 重要：**反向那一邊最容易漏**。ET02 的〈已發布課程不可清空閱課結束時間〉手冊寫了一
> 整段，測試項目卻完全沒驗到——那是會擋掉儲存的行為。寫完測試項目後，一定要回頭把
> 手冊讀一遍。

## 三、需要補拍截圖時

1. 在 `docs/manuals/_shots/{作業碼}-待拍清單.md` 開出清單（**一支作業一個檔案**），
   **五項齊備**：登入身分、資料準備、操作步驟、拍攝範圍、指定檔名，並於開頭載明
   存放路徑。撰寫要求見 [截圖作業指引.md](截圖作業指引.md) 第五節
2. 拍攝者依清單拍好、存入 `_images/{模組}/`
3. 撰寫者插入 md、重新產出、**逐張看過圖與文字是否相符**
4. 拍完即**刪除該清單檔**；`_shots/` 下尚存的清單，就是目前仍待拍的

> 重要：待拍清單**不要寫進〈截圖作業指引〉**。該檔是長期規範，多人並行各做不同作業時
> 共改一份必然衝突；清單是暫時性資產，拍完就該消失。

寫清單時要把「做不出那個畫面」的前提也寫進去。例如「重置重考次數」那張，該學員必須是
**次數已用盡且未及格**——還有剩餘次數時按鈕是停用的，根本拍不到。

資料準備盡量給**具體資料**（課程名稱、學員帳號、章節數與作答次數），不要只寫「一門已發布
的課程」——讓拍攝者到現場才開始找資料，是最容易卡住的一步。

## 四、修改既有文件

改 md → 檢查 → 重新產出，順序固定：

```bash
python docs/manuals/tools/check_manual.py                        # 單檔格式
python docs/manuals/tools/gen_manual.py "docs/manuals/et/ET02-課程建立與編輯.md"
python docs/manuals/tools/gen_acceptance_form.py "docs/manuals/_tests/ET-教育訓練文件管理模組.md"
python docs/manuals/tools/check_consistency.py                   # 跨檔一致性（交付前）
```

> 重要：產出時**指定你要產的那一份**，不要傳入整個 `docs/manuals` 目錄。目錄模式會
> 重產全部手冊，而 docx 即使內容沒變，二進位每次都不同，會讓沒動過的檔案全部顯示
> 為已修改，看不出這次到底改了什麼。需要全部重產時（例如樣式範本調整過）才用目錄。

**畫面改版後**要回頭檢查手冊：按鈕或欄位改了嗎？截圖過期了嗎？這兩件檢查工具都驗不到。

### 兩支檢查工具的分工

| 工具 | 驗什麼 |
|---|---|
| `check_manual.py` | **單檔格式**：圖片路徑、表格欄數、標題層級、禁用字樣 |
| `check_consistency.py` | **跨檔關係**：Word 是否舊於來源、手冊與測試項目之作業覆蓋、同一作業在檔名／標題／測試章節三處名稱是否一致、孤兒圖片、待拍清單是否結清 |

## 五、常見狀況

| 狀況 | 原因與處理 |
|---|---|
| 產出時出現 `Permission denied` | 那個 Word 檔正開著，關掉再跑 |
| 印出「有 N 項內容未進入 Word」 | 該段語法產生器不認得而被略過，比對列出的內容修正 md |
| 檢查報「圖片不存在」 | 路徑錯或圖還沒放進 `_images/` |
| 檢查報「標題不可自行編號」 | md 裡寫了「壹、」「一、」，拿掉，編號由程式產生 |
| 檢查報「含訊息代碼」 | 把代碼換成訊息原文 |
| Word 目錄頁碼是舊的 | 首次開啟會自動更新；未更新按 Ctrl+A 再 F9 |

## 六、交付前檢查

以規範第十節的清單逐項確認，其中**只有前兩項機器驗得到**，其餘要人看：

- [ ] `check_manual.py` 無錯誤
- [ ] `check_consistency.py` 無錯誤
- [ ] 產出時印出「內容核對通過」
- [ ] 按鈕、欄位、選單名稱與現行畫面一致
- [ ] 每張圖都是現行版，且與周邊文字相符
- [ ] 截圖無個資，或已使用遮罩版
- [ ] 無圖示符號、訊息代碼、內部識別
- [ ] 測試項目與手冊所述行為一致，且手冊的重要行為都有對應測試

> 重要：**產得出來不等於寫得對。** 把【新增測驗】寫成【新增測驗題】，檢查會通過、Word 會
> 順利產出、錯誤會一路送到院方手上。最後一關一定是人看過。
