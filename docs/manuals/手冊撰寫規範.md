# 操作手冊撰寫規範

本規範適用於 `docs/manuals/` 下之全部操作手冊與測試項目。目的是讓 27 支作業的手冊
在用語、結構與版面上一致，並可由程式一次產出院方格式之 Word 檔。

---

## 一、產出與來源

來源只有 md，**Word 一律重新產生、不得手改**。兩種產出的粒度不同：

| 檔案 | 粒度 | 用途 | 產生方式 |
|---|---|---|---|
| `et/ETxx-作業名.md` | **一支作業一檔** | 操作手冊原稿 | 手寫 |
| `et/ETxx-作業名.docx` | 一支作業一份 | 交付院方之操作手冊 | `gen_manual.py` |
| `_tests/{模組碼}-{模組名}.md` | **一個模組一檔** | 測試項目原稿，內含各作業 | 手寫 |
| `測試報告/{模組碼}-{模組名}.docx` | 一個模組一份 | 驗收用測試報告 | `gen_acceptance_form.py` |

> 注意：**操作手冊一支作業一份、測試報告一個模組一份**。前者發給操作人員、按作業分發；
> 後者供驗收簽核，一個模組一份文件、其中每支作業各一張表。

手改 docx 的內容會在下次產生時全部消失——**修改一律改 md**。

產出之 docx **納入版控**，未安裝 Python 環境者可直接自 repo 取用；惟其為二進位檔、每次重產皆生成新版本，故**不必每次修改都提交**，定版時提交即可。

### 作業順序

md 是唯一來源，**先把 md 改對，再產生 Word**。順序固定：

```bash
python docs/manuals/tools/check_manual.py                     # 1. 檢查格式與禁用字樣
python docs/manuals/tools/gen_manual.py docs/manuals          # 2. 產出手冊
python docs/manuals/tools/gen_acceptance_form.py              # 3. 產出測試報告
```

Word 開著該檔時無法覆寫，產生前請先關閉。

產生器每次產出後會**自我核對**：逐項比對 md 的每一段文字是否都進入 Word，缺漏即列出。
印出「內容核對通過」才表示 Word 與 md 一致；有缺漏通常代表該段語法產生器不認得而被略過。

> 重要：檢查工具只驗機器判得出來的部分（圖片是否存在、表格欄數、標題層級、禁用字樣）。
> **內容是否與系統一致驗不到**——把【新增測驗】寫成【新增測驗題】，檢查會通過、Word 會順利
> 產出、錯誤會一路送到院方手上。按鈕、欄位、訊息文字一律對截圖或實機核對。

## 三、章節骨架

固定三章，順序不變。作業本身沒有的內容可省略該節，但不新增章：

```
壹、作業說明
  一、使用情境      作業目的、誰能用、在流程中的前後銜接
  二、進入路徑      側邊選單路徑

貳、操作說明        依實際作業順序排列，畫面說明就地嵌入
  一、畫面與前置設定
  二～N、各操作方式與步驟
  N+1、確認送出
  N+2、結果檢視

參、常見訊息與處置
  一、被擋下（動作沒有完成）
  二、有警告（動作完成但需判斷）
  三、送出後的結果訊息
  四、其他情況
```

- 章節編號（壹／一／（一））由產生器自動產生，**md 裡不要自己寫編號**
- 不另立「操作案例」章——案例與步驟重複；有差異的情況寫成步驟底下的一節
- 不另立「注意事項」章——提醒要就地寫在相關步驟旁，放在最後沒人翻得到

## 四、寫什麼、不寫什麼

取捨只有一個判準：**這件事，看畫面看得出來嗎？**

| 看得出來 | 不寫 |
|---|---|
| 欄位叫什麼、有哪些按鈕、清單有幾欄 | 複述畫面，讀者自己看得到 |
| 「章節＝課程的段落」「學員＝上課的人」這類同義反覆 | 讀者是第一線業務人員，比撰寫者更熟這些名詞 |

| 看不出來 | 一定要寫 |
|---|---|
| 這個值是哪裡來的、為什麼各列不同 | 例：測驗成績取該學員歷次作答的**最高分**，不是最後一次 |
| 做了會怎樣、不做會怎樣 | 例：重置重考次數會讓該學員的既有成績重新計算 |
| 為什麼被擋、擋了要怎麼辦 | 即〈常見訊息與處置〉整章 |
| 系統在背後做了什麼判斷 | 例：閱課結束時間會在按下發布的當下重新檢查一次 |
| 資料的範圍與時效 | 例：學習狀況是**查詢當下**即時計算，不是每日結算 |

> 重要：手冊寫得細不是問題，細錯地方才是。描述畫面看得到的東西不會讓手冊更有用，
> 只會讓真正重要的那幾句被埋在裡面。

**欄位說明表**只列「看不出來」的欄位，其餘一句「由系統自動帶出」帶過；
整張表若沒有一欄需要解釋，就不要放表。

### 技術性失敗不寫

連線中斷、服務暫時不可用、請求逾時等**技術性失敗之情境，手冊與測試項目一律不寫**。

理由：測試人員無從製造該情境（須拔除網路、停用後端或攔截請求），列入測試項目只會
卡住；而手冊若單方面寫了、測試項目卻沒有，交付時難以說明為何未驗。兩邊同進同出，
不留落差。

| | |
|---|---|
| ✗ | 上傳影片因連線異常而中斷時，系統以不自動消失之訊息告知 |
| ✗ | 無法取得課程資料，請稍後再試 |
| ✓ | 上傳超過影片大小上限之檔案，系統擋下並提示上限為多少 |

⚠️ **業務規則所致之擋下仍要寫**，縱其訊息文字近似。判準在於「該情境是否由使用者
的操作與資料狀態決定」——是者為業務行為，須寫；僅由系統或網路狀態決定者不寫。

## 五、Markdown 寫法

### 標題層級

| md | 產出 | 用途 |
|---|---|---|
| `#` | 封面之作業名 | 每檔一個，格式為「ET02 課程建立與編輯」 |
| `##` | 壹、貳、參 | 章 |
| `###` | 一、二、三 | 節 |
| `####` | （一）（二） | 小節 |
| 整行粗體 | 操作子標題 | 節內的小主題，不進目錄 |

### 提醒框

以引用（`> `）撰寫，開頭固定兩級，**不使用任何圖示符號**：

```markdown
> 注意：一般提醒，知道比較好。
> 重要：不遵守會導致資料錯誤、漏看或作業卡住。
```

引用系統訊息原文時**加上引號**，與提醒框區分（檢查工具據此判定）：

```markdown
> 「此課程已關閉，無法作答」
```

同一節的提醒框不超過三個；超過表示內容該改寫成步驟或表格。

### 條列

- 有序步驟用 `1.` `2.`，編號原樣輸出，不使用 Word 自動編號
- 步驟中間可插入提醒框或圖片，不會打斷編號
- 無序條列用 `-`，產出為「˙」

### 表格

- 表頭必填，產出為粗體
- 儲存格內換行用 `<br>`
- 欄數以四欄為上限，過寬在 A4 會擠壓

### 圖片

```markdown
![圖說文字](../_images/et/et02-04.png)
```

- 圖說**必填**，會輸出為圖片下方置中的 10pt 說明
- 圖說寫「使用者做了什麼 → 系統給了什麼」，不要只寫畫面名稱
- 每個關鍵動作配一張圖；純文字說得清楚的不配圖

## 六、圖片規範

| 項目 | 規則 |
|---|---|
| 來源 | 實測截圖，複製到 `_images/{模組}/` 再引用，**不直接引用桌面路徑** |
| 命名 | `{作業碼小寫}-{兩位序號}.png`，例如 `et02-04.png`，序號為手冊自己的流水號 |
| 個資 | 含學員姓名、Email、具名問卷填答、個別成績者**一律使用遮罩版**；新增截圖必須先確認畫面無個資 |
| 內容 | 需與現行畫面一致，取用前 MUST 依下列步驟確認 |

手冊圖片自成一套編號，**不沿用實測報告的截圖編號**，避免兩邊發號互相干擾。

> 重要：個資密度最高的是 **ET03 學員**——該畫面同時含學員姓名、個別成績、逐題作答明細
> 與**具名**問卷填答，拍圖前務必先確認已遮罩。DP05 使用者管理、DP09 操作記錄查詢亦含
> 姓名與 Email。

### 缺圖時另行截圖

手冊所需畫面缺哪張就拍哪張，於〈截圖作業指引〉開出待拍清單（登入身分、資料準備、
操作步驟、拍攝範圍、指定檔名五項齊備），拍攝者照著拍。

手邊若有既有截圖可用（例如實測過程留存者），取用前 MUST 依下列步驟確認為現行版。

### 如何確認截圖仍為現行版

> 重要：**圖說看起來對，不代表畫面沒變過**。挑圖一律先比日期，不可只看圖說。

1. **查截圖日期**（`ls -l` 的檔案時間），記下年月日
2. **查該作業最後一次畫面異動**：`grep -oE "2026-[0-9]{2}-[0-9]{2}[^）]*" docs/specs/et/spec_usN.md`
   看裁示日期與內容，判斷哪幾次會改變畫面（新增欄位、新增按鈕、移除功能）
3. **截圖日期必須晚於最後一次會改變畫面的異動**，否則不可使用
4. 同一作業有多批截圖時取**最新**者——首次實作時所拍的通常已不符現況
5. **判斷不出來就重新截圖**，不要猜

**實例**：ET02 於 2026-09-15 起，新增課程時「新增教材」／「新增測驗」由停用改為可直接點（會自動存草稿後繼續），原先那句「請先儲存草稿後再新增項目」的提示同時移除。9-15 之前拍的圖上，那兩顆按鈕是灰的、還帶著那句提示——照著寫等於教使用者一個已經不存在的限制，而檢查工具驗不出來。同日 ET03 也新增了「CSV 已匯出」提示與移除作答中學員的橘色警告框，舊圖同樣沒有。

**不可使用之截圖**：含開發者工具（DevTools）面板、含測試過程留下的文字（如原因欄填「回測 XXXX」）、非通過態之錯誤畫面（除非該章節正是在說明該錯誤）。

需補拍時，於 `截圖作業指引.md` 開出待拍清單（登入身分、資料準備、操作步驟、拍攝範圍、
指定檔名五項齊備），拍攝者不需自行判斷要拍什麼。

| 情境 | 用語 |

> 沿用範本殘留的舊分類。

## 八、禁止事項

以下一律不得出現在手冊與測試項目中：

| 項目 | 原因 |
|---|---|
| 圖示符號（表情符號、色塊） | 正式交付文件；換字型或列印時顯示不一致 |
| 訊息代碼（如 `ET-MSG-ET02-203`） | 屬內部識別，畫面上不顯示，使用者看不到也報不出來；改引訊息原文 |
| 資料表與欄位名稱（如 `ET_ENROLLMENT`） | 同上，屬內部識別 |
| issue／PR 編號、程式檔名行號 | 內部資訊 |
| 內部角色代號（dev／SD／SA） | 必要時寫「開發團隊」 |
| 測試流程用語（首測／複測／回測） | 對外文件不寫測試過程 |
| 錯誤代碼（如 `ET_COURSE_009`、`DP_MAIL_009`） | 屬內部識別，畫面上不顯示；改引訊息原文 |

## 九、測試項目

寫在 `_tests/` 下，**一個模組一個檔案**，與手冊分開維護。結構固定：

```markdown
# 教育訓練文件管理模組      ← 文件標題，用於封面

## ET02 課程建立與編輯      ← 一支作業一節，產出時各成一張表
### 測試前準備
| 項目 | 說明 |

### 測試項目清單
| 項次 | 測試內容 |

## ET03 學員
### 測試前準備
### 測試項目清單
```

> 重要：第一行 `# ` 的文字**就是封面印出來的模組名**（`gen_acceptance_form.py` 的
> `parse_module()` 讀該行，檔名只在無此行時充當備援），故必須寫第七節「用語規範」表中
> 的全稱，⛔ 不可沿用其他專案的模組名。

- 新增作業時**在同一檔案追加一節**，不另開新檔
- 項次於**各作業內自 1 起算**，不跨作業連號
- 每項為**一句可判定合格與否**的陳述，寫成「做什麼 → 系統應如何反應」
- 一句約 30～60 字，過長在表格內會換行過多
- 涵蓋主流程、各類業務檢核與結果呈現（權限擋下屬共通行為，見〈共通行為不列〉）
- 需要特殊條件才能測的項目（兩個以上帳號配合、閱課期間已過之課程、重考次數已用盡且未及格之學員）要在「測試前準備」寫明

### 順序：與手冊一致

測試項目**依手冊之章節順序排列**，使用者看著手冊逐節操作、逐項驗證，項次即隨之
遞增，不必在數十項中尋找現在測到哪裡。

⚠️ 後續補充之項目 MUST 插回其所屬章節之位置，⛔ 不逕自附加於末尾——附加雖省事，
但一支作業補過幾輪之後，順序與手冊即完全對不上，而這件事沒有工具驗得出來。

### 〈常見訊息與處置〉章不列測試項目

手冊第三章寫的是**訊息呈現與處置指引**，非使用者主動執行之操作；逐則列為測試項目
會使項數倍增，而使用者於驗收時面對數十項難以逐條完成。

**唯一例外**：該擋下若未生效，**已落庫之業務資料即錯誤或前後不一致**者，仍列一項。

| | 例 | 列不列 |
|---|---|---|
| 已落庫資料之錯誤寫入 | 已發布課程之閱課結束時間未擋下清空 → 課程永不關閉、學員無限期作答 | **列** |
| 跨作業之狀態一致性 | 新增章節後完課學員之狀態未回退 → ET03 之完課率與實際不符 | **列** |
| 已凍結資料被改動 | 已有學員填答之問卷題目未擋下修改 → 既有填答對不上題目 | **列** |
| 重複寫入 | 同一學員重複加入同一課程未擋下 → 母體多算、閱讀率失真 | **列** |
| **表單必填與格式驗證** | 課程名稱未填、描述超過 500 字、訖止時間早於起始 | 不列 |
| 同類檢核之變體 | 「起始時間不可早於現在」與「已開課不可往前調」同屬時間界線，擇一即足 | 不列 |
| 權限擋板 | 學員帳號進入課程編輯遭擋下——屬共通行為，見〈共通行為不列〉 | 不列 |
| 操作分支之呈現 | 邀請 Email 含未建立帳號者時列出待加入清單 | 不列 |
| 極短時間窗 | 按下儲存至結果訊息出現前按鈕停用 | 不列 |

⚠️ **表單驗證與業務檢核之別**：前者在送出前擋下、使用者補填即過，錯不了資料；
後者擋的是**資料之間的關係**，未擋即落庫且事後難以察覺。⛔ 不可因「兩者都是擋下」
而一併列入——必填驗證逐條列出，正是項數倍增之主因。

### 純呈現不列

判準：**該呈現若不正確，使用者會不會因此做錯下一步？**

| | 例 | 列不列 |
|---|---|---|
| 呈現即決策依據 | ET03 之平均成績顯示「—」而非 0——0 分與未作答意義相反，據以判斷要不要重置 | **列** |
| 呈現即決策依據 | 學員之完課進度（已完成章節／總章節）——據以判斷要不要催 | **列** |
| 清單之排序規則 | 課程列表依建立時間由新到舊、章節依排序值由小到大 | 不列 |
| 查詢條件之預設值 | 進入課程列表預設只顯示自己建立的、狀態預設全部 | 不列 |
| 清單有哪些欄位 | 逐列顯示課程名稱、狀態、建立者、章節數、學員數…… | 不列 |
| 空清單之文案 | 尚無課程時提示點新增建立 | 不列 |

⚠️ 一句之中若**混有呈現與行為**，⛔ 不可整項刪除——刪了會連行為一併丟失，應改寫
為只留行為。例：「作答明細正確顯示題目、學員作答、正確答案、對錯與得分」改為
「點某次作答可展開逐題明細，內容與該次作答當時之題目快照一致」。

> 重要：不列測試項目**不表示手冊可以不寫**。手冊第三章照寫——使用者遇到訊息時要
> 查得到怎麼辦；兩者讀者與用途本就不同。

### 每一項都要寫得出「怎麼做」

測試報告採院方附表 7，只有「項次｜測試內容｜合格｜不合格」四欄，**沒有獨立的操作
步驟欄**——「怎麼做」必須寫進測試內容那一句的前半，且動作一律指向畫面上的實際字樣
（【儲存草稿】【新增教材】【發布】）。

| | |
|---|---|
| ✗ | 章節清單正確顯示各章節之項目數 |
| ✓ | 於章節下【新增教材】並儲存，該章節之項目數即時加一 |

前者只描述了狀態，測試人員不知道要做什麼才看得到那個畫面。

### 測試前準備要給得出資料

⛔ **MUST NOT 以「由資訊人員預先備妥」一語帶過**——測試當天才發現備不出來，整項
就卡住。條件複雜者並註明**為什麼**需要該條件。

| | |
|---|---|
| ✗ | 一門已發布的課程 |
| ✓ | 已發布、閱課期間仍在進行中、且**已有學員完課**之課程一門（完課狀態用於驗證新增章節後回退為進行中，沒有完課者驗不到） |

可查詢資料庫者直接查出具體值（課程名稱、學員帳號、作答次數）填入；不可查者附上
查詢用 SQL 供代查。

### 共通行為不列

各作業共通之行為——登入與權限、側欄與模組切換顯示、成功／失敗提示、確認對話框
之按鈕與執行中行為、清單分頁、個資遮罩、日期界線——**一律不列入測試項目**。該等
行為由共用元件承載，非某一支作業之驗收標的。

⚠️ **本項為刻意之取捨，非疏漏**：這些行為在驗收報告中沒有對應項目。需要證明已驗
時，另依實測紀錄說明，⛔ 不因此回頭把它們補進各作業——一旦各模組各列一遍，數十條
乘以模組數，徒增測試人員負擔而未提高覆蓋。

模組專屬之行為（例如 ET02 檢視模式那條「由誰建立」的 banner）仍寫在該作業節內。

### 模組覆蓋

**有手冊的作業，測試項目檔就必須有對應章節**——缺一支即缺一張驗收表。

⛔ **不要求涵蓋對照表上尚未撰寫手冊之作業**：各作業係陸續完成，若要求全覆蓋、以
「尚未開發」佔位，檢查將長期為紅，久之即被忽略——那比沒有檢查更糟。某模組宣告
完成時，再以對照表逐支核對。
