# API Error Code 對照表

> **骨架（2026-07-09 建立）**：本檔隨各實作 task 增補——每張 issue 新增自己用到的錯誤碼，不一次寫全。
> 命名規範見 [`.claude/rules/sti-error-codes.md`](../../.claude/rules/sti-error-codes.md)。

## 格式說明

- **命名規則**：`{頂層模組}_{子功能}_{流水號}`
- **頂層模組（EDMS）**：`DP`（平台）/ `ET`（教育訓練）/ `DM`（文件管理）/ `COMMON`（跨模組通用）
- **子功能**：全大寫英文（如 `AUTH` / `USER` / `PARAM` / `MAIL`）
- **流水號**：三位數字 `001`~`999`，由 001 起**連續**編號（不跳號）
- **框架層 HTTP 錯誤**：`HTTP_{status_code}`（如 `HTTP_404`、`HTTP_405`）
- **回應格式**：

```json
{ "error_code": "DP_AUTH_001", "error_message": "帳號或密碼錯誤" }
```

由 `core/exceptions.py` 的 `AppError` + `main.py` 的 `app_error_handler` 統一處理。

### 新增流程

1. 於本檔對應模組表格加新列（流水號取該子功能區塊最大號 +1）
2. 實作處 `raise AppError(status_code=..., detail=..., error_code="DP_XXX_001")`

### 設計原則（安全）

- `error_message` 固定為**靜態字串**，**不嵌入動態值 / 欄位名稱**（防 Log Injection、不洩漏 schema）
- Pydantic 驗證失敗（`COMMON_422`）**不回傳欄位名稱或驗證細節**；完整錯誤只寫伺服器端 debug log

> **註**：`sti-error-codes.md` 規則檔的模組清單為 TBMS 沿用（含 BC/CP/TL/BS/MA），EDMS 實際只有 **DP / ET / DM / COMMON**；規則檔模組清單待另行對齊（follow-up）。

| COMMON_002 | 422 | page 必須 >= 1 |
| COMMON_003 | 422 | limit 必須 >= 1 |
| COMMON_004 | 422 | limit 不得超過 100 |
| COMMON_005 | 400 | 不允許更新的欄位 |
| COMMON_422 | 422 | 請求格式驗證失敗 |
| COMMON_429 | 429 | 操作過於頻繁，請稍後再試 |
| COMMON_500 | 500 | Internal Server Error |
| COMMON_503 | 503 | 系統忙碌中，請稍後再試 |

> **`COMMON_503`**：密碼運算（bcrypt）之併發閘負載卸除（#214）。同時進行中的運算達門檻時
> 立即拒絕，避免請求在等待期間持續佔用 DB 連線。屬**暫時性**錯誤，前端可提示稍後重試；
> 勿用於一般系統錯誤（那是 `COMMON_500`）。

> **框架層 HTTP 錯誤**（非 AppError，如路由不存在 / Method Not Allowed）：error_code 為 `HTTP_{status_code}`（如 `HTTP_404`、`HTTP_405`）。

> `DP_AUTH_007` 與 `DP_AUTH_010`（登入防帳號列舉，#208）：`DP_AUTH_007` 涵蓋「查無有效 `DP_USER` 列」的**全部**情形——完全不存在、自助註冊未驗證、管理者已邀請、待驗證列已逾期——四者的 status / error_code / error_message 完全相同。
>
> 分開回應會讓匿名者**密碼隨便填**即可問出某 Email 是否有待驗證列，而 `ADMIN_INVITE` 列同樣命中，等於開放列舉「組織邀請了誰」。`DP_AUTH_010` 原是 #56 為避免未驗證者看到誤導的「查無此帳號」而設，引導需求仍在，但改由**一句涵蓋全部出路的中性訊息**承接，不靠「只對這類人顯示」。因此該訊息中的三個指引（註冊 / 點驗證連結 / 重寄）是**驗收條件而非文案偏好**，缺一即有一類使用者無路可走。
>
> 能區分四者的只剩**稽核 reason**（`DP-AUTH` / `FAIL` 的 description：「帳號未驗證」vs「帳號不存在」）——對外統一、對內可追溯，兩者刻意脫鉤。
>
> ⚠️ **仍可區分的殘留**：`DP_AUTH_008`（已驗證帳號、密碼錯）與 `DP_AUTH_007` 不同，故「某 Email 是否為已驗證帳號」依然可探測。這是 #208 AC 2 明訂保留（鎖定計數與既有 UX 掛在該路徑上），非遺漏。`DP_AUTH_010` 依本檔「流水號不跳號」原則保留為退役列，不刪除。
>
>
> `DP_USER_001` 與 `DP_USER_011`（註冊防帳號列舉，#208）：同一問題的另一道門。`DP_USER_011` 原表示「該 Email 有未逾期的管理者邀請」，是全系統**唯一**會單獨揭露 pending 列 `KIND` 的訊號——login 收斂之後，攻擊者仍可從 `/api/register` 分辨出「這個 Email 是管理者發出的邀請」，而那正是最有價值的一格（那批人此刻正在等一封啟用信、還沒設過密碼，對他們發仿冒啟用信的成功率遠高於盲發）。
>
> 該訊息的措辭原本就刻意不提「管理者邀請」，但 `app_error_handler` 會把 `error_code` 一起放進回應本體——**文案上的模糊只對人類有效，對腳本一清二楚**。現併入 `DP_USER_001`：**單看註冊端點**可分辨的只剩「{已註冊 或 已受邀} vs 其他」。
>
> ⚠️ **這一格並未真正關閉，只是探測成本從 1 個請求變成 2 個。**「未逾期邀請」仍可由 login 與 register 交叉比對取出：
> `/api/login` 回 `DP_AUTH_007` ⇒ 無未刪除的 `DP_USER` 列；`/api/register` 回 `DP_USER_001` ⇒ `DP_USER` 列存在（**含軟刪**）或有未逾期邀請。兩者交集 = `{未逾期 ADMIN_INVITE}` ∪ `{軟刪除的 DP_USER}`，而後者在本專案是**空集合**（系統無刪除使用者功能，`DP_USER.DELETED` 從不被設定），於是交集就是邀請名單本身。
>
> 根治需讓「未逾期邀請」離開 409 集合（例如回與正常註冊同形的 202、不寄信也不覆蓋邀請列），那會動到 `spec_us2` AC 6a 與 FR-02/03 的對外行為，**追蹤於 #345**。此處如實記載並以測試釘住，使它是**已知且被守衛的殘留**，而非被誤以為已關閉。
>
> 合併後的訊息必須同時鋪出**登入**與**點信中連結**兩條路：受邀者沒有 `DP_USER` 列，舊訊息叫他「使用忘記密碼」會落進防列舉的靜默 no-op，等於死路。
>
> ⚠️ 兩個檢核必須在**同一步**執行（皆置於 `assert_email_available`，冷卻 check 之前）。若一個擋在冷卻前、一個擋在冷卻後，冷卻武裝時會分別回 409 與 429，**位置差本身就重建了 oracle**。

> `ET_SURVEY_003`（題目凍結，#204）：`ET_SURVEY_RESPONSE_M` 存在任何未刪除紀錄即凍結，為**應用層**檢核而非 DB constraint。凍結僅涵蓋題目與選項之增改刪與重排；問卷名稱與 `IS_ACTIVE` **不受限**——AC 21 明訂此時教師僅可停用問卷，連停用都擋掉會使凍結後無路可走。
>
> `ET_SURVEY_004` 與 `ET_QUESTION_003` 看似同類但**規則不同**：問卷選項為「至少 2、**無上限**」（`data-model` §ET_SURVEY_OPTION 未訂上限），測驗選項為「2–6」。共用單一代碼會讓兩者的界限在維護時互相污染。
>
> `ET_PUBLISH_001`（#204）：回應除 `error_code` / `error_message` 外另帶 `blockers` 陣列（`code` / `message` / `target_id`），對應 ET-MSG-ET02-011 之「{缺漏項目}」。`message` 一律為靜態文案、**不內插測驗名稱等使用者輸入**，出問題的對象以 `target_id` 表達。

> `ET_COURSE_006` ~ `008`（#288 關閉與再開課）：
>
> - **`006` 與 `007` 不共用**：兩者的下一步不同（「這門課還沒發布」→ 去發布；「這門課已經關了」→ 去再開課），共用會讓前端只能顯示一句模稜兩可的訊息。措辭比照 `ET_COURSE_005` 那種「這個狀態不給做，請改用另一個動作」的形狀。
> - **`006` 為 409 而非 422**：它擋的是狀態機沒有那條邊（草稿沒有學員也沒有邀請碼，關閉它沒有語意；已關閉再關一次會把 `CLOSED_AT` 覆蓋成第二次點擊的時間），與 `ET_PUBLISH_002`（課程狀態不允許發布）同一性質。
> - **`008` 檢核「訖止 > 當下」，而課程編輯的 `_CourseFields` 刻意不檢核「起始 ≥ 當下」**：後者有 2026-08-24 裁示——已發布課程的起始必然落在過去，無條件檢核會讓教師之後編輯該課程時因沿用原值而永遠存不了檔。那個理由在再開課不存在（FR-ET-US11-09 明訂強制重設）。若不檢核，直呼 API 就能造出「已發布但期間已過」的課程：教師端看到「已發布」，學員端卻被 `is_effectively_closed` 判為視同關閉而進不去，**狀態自相矛盾且沒有任何地方會察覺**。
> - **`008` 只檢核訖止、不檢核起始**：起始允許落在過去——「補開一段已經開始的期間」是合理操作。
> - **再開課會重跑發布六項檢核**（SA Q2 裁示 A），不合格回 `ET_PUBLISH_001` + `blockers`（與 `publish` 共用同碼與同一份缺漏清單形狀）——關閉期間教師端仍可編輯內容，課程可能已不符發布條件。
> - **`ET_INVITE_004` 與 `ET_INVITE_002` 在寄邀請時分流**（#288）：草稿 / 已關閉回 `004`（僅已發布課程可邀請學員）；**已發布但閱課期間已過**回 `002`（此課程目前關閉中）。共用 `004` 會對一門 `STATUS` 確實是 `PUBLISHED` 的課程說出一句與教師畫面矛盾的話。

> `ET_INVITE_001` / `006` / `007` 已於 #362 廢止，**編號不重用**：
>
> | 代碼 | 原訊息 | 為何消失 |
> |---|---|---|
> | `ET_INVITE_001` | 邀請連結無效或已失效 | `POST /et/invitations/accept` 整個端點移除——邀請即加入，沒有要「接受」的東西 |
> | `ET_INVITE_006` | 此邀請已撤回 | 沒有待加入列可撤回；寄錯人改用 US9 的「移除學員」 |
> | `ET_INVITE_007` | 邀請信寄送失敗，請稍後再試 | 寄信失敗**不再是錯誤回應**：人已經加入了，失敗的只有通知信，故改以 200 + `mail_failed` 清單呈現 |
>
> 留號不重用的理由與 `ET_APPROVAL_*` 當初重新編號的情況相反：那次是尚未交付的代碼在同一支 PR 內收斂；這三支**已經出現在正式環境的回應與前端判斷裡**，重用同一個號碼會讓舊前端把新情境當成舊訊息顯示。
>
> ⚠️ `ET_INVITE_005`（Email 尚無帳號）在 #362 之後**不只是防呆**：它是「邀請即加入」成立的前提——正因為收件人一定是既有帳號，才能在寄信當下就寫 `ET_ENROLLMENT`。放寬它必須連帶重新檢討整個決策。

> `ET_INVITE_008`（帳號已停用，#362 一併處理 #347 第一項）：**編號從 008 起跳**，因為 006 / 007 雖已廢止但留號不重用（見上）。
>
> - **與 `005` 分碼**：兩者的下一步完全相反——「請管理者建帳號」對一個已經有帳號的人是錯的指示，教師照做會得到一個重複帳號。
> - **只擋「停用」、不擋「鎖定中」**：`LOCKED_UNTIL` 是連續登入失敗的暫時性鎖，幾分鐘後自動解除；因為某人剛才打錯密碼就拒絕教師邀請他，教師無從理解。故判定用 `is_account_disabled()` 而非 `is_account_usable()`。
> - **為何 #362 才需要它**：`DP_USER.DELETED` 從不被設定，停用一律走 `STATUS`，所以原本的 `DELETED = 0` 過濾對停用者無效。#362 之前停用者被 `accept` 擋在 403、只會停在待加入清單上讓教師看見；取消待加入之後他會被直接寫進 `ET_ENROLLMENT`，而 ET03 清單與週報只濾 `IS_REMOVED` / `DELETED`——一個永遠不可能完課的帳號會**永久坐在完訓率的分母裡**。

> `ET_SURVEY_007`（#238）：措辭刻意比照 `ET_COURSE_005`（「僅草稿課程可刪除，已發布課程請改用關閉」）——同一種「這個狀態不給刪，請改用另一個動作」的語意，訊息形狀一致教師才不用重新理解。「已關閉」也擋：關閉可逆，若允許在關閉期間刪問卷，再開課後學員的填答入口會無故消失。
>
> `ET_SURVEY_011` ~ `017`（#284 學員填寫端）：
>
> - **`011` 與 `ET_LEARN_002` 同語意但分碼**——後者的註記明寫「只用於 `/courses/{id}/learn`」，共用會讓那條註記失效。學員端問卷以 `course_id` 定址（一門課程 0~1 份問卷），與 `/learn` 同樣「課程的存在對學員不是秘密」，故亦用 403 而非 404。
> - **`011` 與 `012` 不共用**：「你不在這門課」與「你還沒完課」的下一步完全不同（去加入 / 去把課上完），共用會讓前端只能顯示一句模稜兩可的訊息。
> - **`012` 涵蓋「未完課」與「問卷未啟用」兩種**：兩者對學員的下一步都是「先把課上完」，而問卷有沒有被停用是教師端的事，告知他反而只會讓他去問教師一件他無法處理的事。
> - **`013` 不是真正的錯誤**：學員開兩個分頁各按一次送出時它是**正常結果**（他的問卷確實已送出），前端收到後改為重載表單轉唯讀、不顯示紅色錯誤。比照 `enrollment` 對重複加入回既有選課列的處理。
> - **`014` 與 `ET_ENROLL_002` / `ET_INVITE_002` / `ET_PROGRESS_001` 同為「課程關閉中」但分碼**：四者子功能不同（加入 / 邀請 / 學習進度 / 問卷），且問卷情境的下一步是「等再開課」而非聯繫教師。
> - **`017` 刻意合併四種畸形請求**（選項不屬該題 / 題型與欄位不符 / 題目不存在 / 同題送兩次）：四者都是自家 UI 產不出來的請求，使用者的下一步一律是「重新整理表單」，分碼不會讓前端做出不同的事。相對地 `016`（字數超限）**不併入**——它的修正方向是「刪掉一些字」，與重新整理不同。`SO_ID` 必須驗證屬於該題，否則 US9 的統計會出現不屬於該題的選項，而那份統計沒有任何地方會察覺。
> - **`015` 帶 `extra.unanswered_sq_ids`**：問卷可能有十幾題，只說「有題目未答」前端無法逐題標示。**問答題不列入未答**（FR-ET-US13-03：問答題為選填）。

> `ET_SURVEY_008` 與 `ET_SURVEY_004` **不可共用**：前者是「問答題不能有選項」、後者是「單選題選項不足 2 個」，兩者的修正方向相反（一個要刪光、一個要再加）。共用單一代碼會讓前端只能顯示一句模稜兩可的訊息。問答題帶選項是**明確擋下**而非靜默忽略——教師把單選改成問答時，選項若被無聲丟棄他會以為還在。

> `ET_ENROLL_001`（#247）：**格式不符與查無共用同一代碼**。8 碼純數字以外的輸入不可能命中（欄位為 `VARCHAR(8)`），拆成兩碼只會告訴嘗試者「這組格式是對的，只是不存在」——那正是枚舉有效邀請碼時想要的回饋。草稿課程之邀請碼（理論上不存在，發布時才產生）亦回本碼而非 `ET_ENROLL_002`，避免向未受邀者確認一門尚未發布之課程存在。
>
> `ET_ENROLL_002`（#247）：判定依據是**課程當前狀態**而非碼是否存在——邀請碼於課程關閉期間失效、再開課後恢復有效（`spec_us4` Clarifications），碼本身自始至終不變。
>
> `ET_ENROLL_003`（#247 SA Q1 裁示 C）：被教師移除之學員**不可自行重新加入**，須由教師重新邀請（`ET-8`）。必須在**應用層**擋下——`ET_ENROLLMENT` 的 `UQ_ET_ENROLLMENT_USER_COURSE` 為全表唯一（刻意，見 `progress/models.py`），放它掉進 INSERT 會變成 500，且衝突對象是一筆學員在前台看不見的列。
>
> **「已加入」刻意沒有錯誤碼**：AC 10 要的是「不重複加入、直接導向該課程」，那是正常導航（ET-MSG-ET04-003 屬「提示」類型），以 `POST /enrollments/preview` 回應的 `already_joined` 表達。用 4xx 表達會讓前端得從錯誤路徑做正常導航。

> `ET_LEARN_002`（#255）**只用於 `/courses/{id}/learn`**：課程的存在對學員不是秘密（他可能正要加入），而「你尚未加入此課程」是可行動的訊息。**以 id 定址的資源端點（教材內容 / 影片檔 / DM 文件檔）一律回 `ET_LEARN_001`（404）**——回 403 等於確認「這個 id 存在，只是你不能看」，可被用來枚舉全站有多少教材、哪些 id 有效。同一個判斷見 `ET_ENROLL_001`。
>
> `ET_LEARN_004`（#280）「您已被該課程移除」——與 `ET_LEARN_002` 同為 403、同樣擋下存取，**差別只在訊息**。被移除者收到「您尚未加入此課程」會以為自己走錯課程、再去找一次邀請碼，而依 #247 裁示 C 他也不能自行加回，那是白費力氣（`spec_us6` 場景 28 的 next navigation）。**只用於 `/courses/{id}/learn`**：其餘呼叫點問的是「能不能拿這份資料」，不需要區分不在籍的原因。
>
> `ET_LEARN_003`（#255）「此內容已刪除」對應 AC 22（教師刪除學員正在檢視之章節）。**它只對有權者顯示**：授權判定走「不濾軟刪除」的反查鏈先確認資格，確認後才回報刪除；無權者得到的是與「不存在」相同的 `ET_LEARN_001`。若順序相反，等於向任何登入者確認「這個 material_id 曾經存在」。
>
> ⚠️ ET 學員端取檔端點的授權是**在籍 OR 擁有者**（#255 SA Q1 裁示 A：教師需能驗收學員視角）。影片與 DM 文件是實體檔案，四個端點**各自**判定、不共用一次查詢結果——共用時新增端點的人容易忘記掛，而該遺漏在測試中不會自然浮現。

> `ET_PROGRESS_001`（#274，#255 SA Q2 裁示的執行點）：課程關閉 = **讀照舊、寫全停**。ET-5a 完全沒有寫入，故那條裁示在當時是自然成立、從未被驗證的；三個進度寫入端點是第一個真正執行它的地方。與 `ET_ENROLL_002`（「此課程目前關閉中」）**刻意分開**——後者是「你不能加入這門課」，前者是「你在課裡，但這次觀看不算進度」，兩者的下一步完全不同。
>
> **教師預覽的寫入一律靜默忽略、回 200 而非錯誤**（#255 SA Q1 裁示之延伸），**故意沒有錯誤碼**。他沒做錯事——擁有者進 ET05 本來就是預覽，跳一個錯誤只會讓他以為預覽功能壞了。判定為「是擁有者且**不在籍**」：教師若真的用邀請碼加入自己的課，他就是學員，關閉照常擋。**此判定必須排在關閉判定之前**，否則教師預覽一門已關閉的課會拿到 `ET_PROGRESS_001`。
>
> `ET_ATTEMPT_001`（#279）：**查無測驗、無權、項目尚未解鎖三者共用同一個 404**。回 403 等於確認「這個 quiz_id 存在，只是你不能看」，可用來枚舉全站有多少測驗；而「未解鎖」若給不同的碼，等於告訴學員「這裡有東西，只是還不能碰」——那正是解鎖要隱藏的資訊。同一個判斷見 `ET_LEARN_001` 與 `ET_ENROLL_001`。
>
> `ET_ATTEMPT_002`（#279）：判定為「本輪已用作答次數 > `MAX_RETRY`」。⚠️ **`MAX_RETRY = 0` 是「只能作答 1 次」，不是「不能作答」**（總可作答次數 = `MAX_RETRY + 1`，見 `quiz/models.py`）——讀成後者會讓所有未設重考次數的測驗全部打不開。**已有未完成的作答時不受此限**：那是「繼續」而不是「開始」，`ATTEMPT_NO` 早已配發（#279 SA 裁示 Q1 = A）。
>
> `ET_ATTEMPT_005`（#279）：**時限的唯一伺服端強制力**。閱卷讀的是 `SELECTED_OPTIONS` 的當前值，而逾時只決定 `STATUS` 標成 `TIMEOUT`——不影響計分。若暫存不擋逾時，學員可以關掉分頁、慢慢查完資料、回來逐題寫入再提交，照樣滿分。擋的是**寫入**、不是**提交**：`spec_us6` 場景 10 要的是「以時間到當下的作答狀態自動提交」，沒收學員已經寫好的考卷不在其中。
>
> `ET_ATTEMPT_006`（#279）：#255 裁示 Q2「關閉 = 讀照舊、寫全停」在測驗上的執行點。**只擋「開新的」**——關閉當下已在作答的 attempt 仍可提交並計分（`spec_us6` 場景 27），故續作分支在此判定之前就先返回了。與 `ET_ENROLL_002`（「此課程目前關閉中」，指不能加入課程）刻意分開：兩者的下一步完全不同。

> `ET_ATTEMPT_003`（#279）：已提交的 attempt 不可再暫存或重複提交。**逾時不走這支**——`spec_us6` 場景 10 要求「以當前作答狀態自動提交」，故逾時提交照常閱卷、僅把 `STATUS` 記為 `TIMEOUT`。拒收等於沒收學員已經寫好的考卷。

> `ET_PROGRESS_002`（#274）：只在**全部**上報區段都落在影片長度之外時才回。單段超界屬正常誤差（`currentTime` 可能略微超過 ffprobe 取得的 `DURATION_SEC`），照 `data-model` 的規定裁切吸收即可。全部超界代表前端上報到錯的 `video_id` 或時間軸算錯——靜默接受會讓這種 bug 表現成「怎麼看都沒有進度」，一個沒有任何訊號、只能靠使用者抱怨才會發現的故障。

> `ET_APPROVAL_001` ~ `005`（#352 線下核可）：
>
> - **沒有「學員尚未完課」的錯誤碼，這是刻意的。** `ET-MSG-ET03-304`「學員尚未完課，無法核可」在 `spec_us16` 裡歸類為錯誤、觸發情境是「場景 3：對未完課學員核可」——但同一個場景 3 又明訂那顆按鈕根本不顯示。核可端點讓單筆與批次走**同一條路徑**（單筆即 `user_ids` 長度為 1），未完課一律回 `skipped[reason=NOT_COMPLETED]`，前端據筆數選訊息（單筆 `304`、批次 `303`）。註冊一個沒有任何地方 raise 的碼，只會讓下一個人去找它不存在的呼叫點。
> - **`002` 與 `ET_TRACK_003` 訊息相同但不共用**：兩者分屬不同端點（核可 / 撤銷 vs 重置重考 / 移除學員），各自模組持有自己的碼是 ET 的既有作法（`ET_INVITE_002` 與 `ET_ENROLL_002` 同樣是「此課程目前關閉中」而不共用）。判定一律用 `is_effectively_closed` 而非比對 `STATUS`——ET-16 的 SCHET002 執行前，期間已過的課程 `STATUS` 仍是 `PUBLISHED`。
> - **`003` 與 `004` 分流**：查無核可紀錄回 `003`（這個人從來沒被核可過），查得到但版本不符或已被撤銷回 `004`（你看到的畫面過期了）。合併會讓前端只能顯示一句模稜兩可的話，而兩者的下一步不同——前者該去核可，後者該重新整理。
> - **`005` 不交給 Pydantic 的 `min_length=1`**：那個放行 `"   "`，而撤銷原因是**事後回答「為什麼這筆核可被推翻」的唯一欄位**（`ET_APPROVAL` 因 `(COURSE_ID, USER_ID)` 唯一而 update 覆寫，前次結果只存在 `DP_AUDIT_LOG`）。且 Pydantic 失敗回 `COMMON_422` 不帶欄位名，前端無從把 `ET-MSG-ET03-305` 掛回那個輸入框。
> - **授權一律沿用 `ET_COURSE_001` / `ET_COURSE_002`**，不自建——判定為 `ensure_owner_or_admin`（owner ∪ 管理者，`FR-ET-US16-07`）。
