> 來源：2026-06-29 客戶會議變動
>
> **SA 裁示（2026-09-02，交付前自檢後對齊平台實作能力）**：
> 1. **KPI 週報不走 email 附件**——平台發信服務不支援附件，週報改「內文摘要 + 儀表板連結」，逐文件明細 CSV 由 DM06 儀表板匯出（FR-004 / AC5）。

> 3. **「應看」母體＝具 `DM_VIEWER` 角色之使用者**（且可見對象相符）；純 EDITOR / ADMIN 而無 VIEWER 者不計入應看，「不排除兼具其他角色」指兼具 VIEWER 者仍算（FR-003）。

## User Story

管理者需掌握各文件之閱讀率（已看 / 未看人數與百分比）作為 KPI：系統於使用者**下載目前發布版**時記錄「已看」，管理者可於 KPI 儀表板（DM06）逐文件即時查看；並由每週排程（`SCHDM001`，執行時間可由管理者設定、預設週一 10:00）寄送 KPI 週報予管理者、寄送未讀提醒予未看之閱覽者（涵蓋統計母體之全部文件；訓練教材除外，見 FR-002）。未讀提醒是否寄送由管理者於通知範本「未讀提醒」啟用 / 停用統一控制（比照 ET），不設文件層個別開關；每週執行時間（星期＋時間）亦由管理者於通知範本設定（比照 ET），KPI 週報與未讀提醒共用。

**Priority**: P2 — 屬管理面稽核 / 落實度追蹤；於文件生命週期（P1）與可見性（US1/US3）上線後配套。

**Independent Test**: 以閱覽者下載某文件目前發布版 → 該文件 KPI 已看數 +1；管理者進入 DM06 見逐文件應看 / 已看 / 未看 / 百分比；對該文件發布新版本後其已看重置；模擬每週排程 → 管理者收到 KPI 週報（內文摘要 + CSV）、未看閱覽者收到彙整未讀提醒（涵蓋統計母體之全部文件，不含訓練教材）；停用「未讀提醒」範本後不寄提醒但 KPI / 週報照常。

### Acceptance Scenarios

1. **Given** 閱覽者於 DM07 下載某文件之目前發布版，**When** 下載完成，**Then** 系統寫入一筆 `DM_DOC_READ`（DOC_ID / VERSION_ID + CREATED_USER＝下載者 / CREATED_DATE＝下載時間）；同人同版本重複下載不重複計人（唯一約束）；**預覽不計**
2. **Given** 管理者進入 DM06 KPI 儀表板，**When** 載入，**Then** 逐文件列出 文件名稱 / 分類 / 應看數 / 已看數 / 未看數 / 百分比，可依關鍵字 / 分類查詢、匯出 CSV；一般使用者導覽不顯示且後端擋直接存取（DM-MSG-DM06-002）
3. **Given** 某文件之應看名單，**When** 計算，**Then** 應看＝該文件可見對象相符之閱覽者（掛「全體」→ 所有閱覽者；OR 比對），**不排除**兼具編輯 / 審核 / 管理者者；已看＝其中已下載目前發布版者（distinct CREATED_USER）；百分比＝已看 ÷ 應看
3a. **Given** 某文件掛了可見對象但無任何閱覽者被授予該對象（應看＝0），**When** DM06 呈現，**Then** 百分比顯示「—（無對應閱覽者）」，且該文件**不列入整體平均閱讀率**計算
4. **Given** 文件發布新版本，**When** KPI 重算，**Then** 改以新版（目前發布版）計算，原僅下載舊版者對新版視為未看
5. **Given** 排程設定之每週執行時間（預設週一 10:00，可由管理者設定），**When** `SCHDM001` 觸發，**Then** 系統計算統計母體（全部已發布文件，不含訓練教材）之 KPI，產生 **KPI 週報**（Email 予所有具 DM_ADMIN 角色者：內文摘要〔總文件數 / 整體平均閱讀率 / 閱讀率**最低前 5 份** / **儀表板連結**〕；逐文件明細 CSV 由 DM06 儀表板匯出、不走 email 附件）
6. **Given** 同一次排程，**When** 產生未讀提醒，**Then** 對**每位有未看文件之閱覽者**寄**一封彙整信**（Email，列出其所有未看文件）；**涵蓋統計母體之全部文件**（不含訓練教材，見 FR-002）；無未看者不寄；若管理者已停用「未讀提醒」範本則整批不寄
7. **Given** 排程需寄大量 Email，**When** 執行，**Then** 收件經平台唯一發信服務、由 outbox `DP_EMAIL_LOG` 背景批次寄送，不阻塞排程主流程
8. **Given** 管理者於平台 DP 後台通知範本停用「KPI 週報」或「未讀提醒」（MODULE=DM），**When** 排程執行，**Then** 對應 Email 不寄（KPI 計算與 DM06 儀表板仍正常）
9. **Given** 某文件掛有多組可見對象，**When** 管理者於 DM06 展開該列，**Then** 逐組顯示「組名 + 應看 / 已看 / 未看 / 閱讀率」；若有人身兼多組致逐組加總大於文件應看，畫面**明示**該差異之成因（FR-003a）
10. **Given** 系統存在分類為 `TRAINING` 之已發布文件，**When** 管理者檢視 DM06、匯出 CSV 或排程執行，**Then** 該文件**不**出現於統計清單 / CSV / 週報總文件數，**亦不**產生未讀提醒；而是列於獨立之「訓練教材」區並**不顯示任何閱讀統計**，區內載明其閱讀由教育訓練模組追蹤（FR-002）

## Functional Requirements

- **FR-001**: 系統 MUST 於使用者下載「目前發布版」時寫入一筆 `DM_DOC_READ`（`DOC_ID` / `VERSION_ID` + 標準 `CREATED_USER`＝下載者 / `CREATED_DATE`＝下載時間）；**預覽不記**；唯一約束 (DOC_ID, VERSION_ID, CREATED_USER) 使同人同版本重複下載不重複計人
- **FR-002**: 系統 MUST 提供 KPI 儀表板（DM06，**僅 DM_ADMIN**，後端擋直接 URL 存取）：逐文件呈現 文件 / 分類 / 應看 / 已看 / 未看 / 百分比，支援關鍵字 / 分類**查詢**與 **CSV 匯出**；範圍為**全部已發布文件，惟排除 `TRAINING`（訓練教材）**
  > **修訂（#567，2026-10-07）**：原文為「範圍為**全部已發布文件**」。訓練教材移出統計母體（儀表板 / CSV / 週報總數 / 未讀提醒四處一致），改以獨立區塊僅列出文件、**不呈現任何閱讀統計**。
  >
  > **理由（必讀，勿依原 FR 文字改回）**：教材之閱讀路徑是 ET06，而 **ET 代學員取檔刻意不寫 `DM_DOC_READ`**（`app/et/common/dm_client.py` 所載之 DM 端 D-2 裁示）。因此 DM 的「已看」只數得到「有人特地進 DM 畫面下載檔案」，與教材是否被研讀無關——**閱讀率在結構上保證低報，方向固定**。一份全班都在 ET 讀完的教材在此仍顯示 0%。給出這個數字比不給更糟：它看起來有權威性，管理者會據以判定「沒人受訓」。
  >
  > 更要緊的是**未讀提醒**：未排除時，掛了可見對象的教材會真的寄信去催閱覽者閱讀一份 ET 教材——那是寄錯信，不只是數字難看。
  >
  > **排除以分類為準**，不以「有無可見對象」為準：前者直接表達上述結構性事實；後者把判準綁在可變的資料狀態上，且漏掉 #377（TRAINING 免填可見對象）之前建立、仍帶著可見對象的既有教材。
  >
  > 本條與 [spec_us5.md](spec_us5.md) FR-009（TRAINING MUST NOT 寫入可見對象）合起來原本就蘊含「TRAINING 的應看恆為 0」，但該後果從未被寫下來，故 FR-002 與 FR-003 一直各自成立卻互相矛盾。
- **FR-003**: 「應看」名單 MUST 為該文件可見對象相符之閱覽者，**母體＝具 `DM_VIEWER` 角色之使用者**（掛「全體」→ 全部 DM_VIEWER；否則文件 AUDIENCE ∩ 使用者可見對象授權 ≠ ∅，OR 比對，per [spec_us3.md](spec_us3.md) FR-008）；**不排除**兼具編輯 / 審核 / 管理者者（指兼具 VIEWER 者仍算入），但**純 EDITOR / ADMIN 而無 VIEWER 角色者不計入應看**（其靠角色可技術性瀏覽，非目標讀者）；「已看」MUST 以是否下載**目前發布版**判定（distinct `CREATED_USER`）；發布新版本後 MUST 以新版重算（舊版已看不計入新版）。**應看＝0**（文件無任何對應閱覽者）時 MUST 顯示「—（無對應閱覽者）」且**不列入整體平均閱讀率**計算
- **FR-003a**（#567，2026-10-07）: DM06 MUST 於逐文件列下提供**逐可見對象組**之完成度（組名 + 該組應看 / 已看 / 未看 / 閱讀率），組名為「全體」／職位名／「單位．職位」。
  - **各組獨立計算**：一位閱覽者同時符合同一份文件之多組配對時（身兼兩職而文件兩組皆掛），**每組分母皆計入該員**，而文件層「應看」維持**去重**。故逐組應看之加總 MAY 大於文件應看。
  - **當逐組加總確實大於文件應看時**，介面 MUST 明示該差異之成因——兩個對不起來的數字在沒有說明時會被判讀為計算錯誤。
    > **修訂（2026-10-08）**：原文要求無條件顯示。實際上身兼多組是少數例外，無條件顯示會讓常態多出一句說明一件沒發生的事，且在兩數相等時印出「加總（2）可能大於本文件應看（2）」這種自我矛盾的句子。改為**僅於差異實際存在時顯示**。
  - 某組應看＝0 時該組閱讀率 MUST 為「—」而非 0%（與文件層同語意）。
  - ⚠️ **取捨（明示而非默認）**：逐組明細僅 DM_ADMIN 可見，但其粒度足以識別單一人員之閱讀行為——某組應看＝1、已看＝0 時，等同指出該名人員未讀該文件。文件層彙總值無此性質。此為管理者職責（落實度追蹤）所需，且 `should_see=1` 之文件於彙總畫面本就有相同效果。
- **FR-003b**（#567，2026-10-07）: 統計卡「閱讀率低於 50% 之文件數」之分母 MUST 為**可計算閱讀率之文件數**（排除應看＝0 者），與分子同母體；不得使用全部文件數。
- **FR-004**: 系統 MUST 提供排程 `SCHDM001`（**每週執行，星期＋時間可設定，預設週一 10:00**；於平台 `DP_SCHEDULE` 註冊表登錄、由平台排程引擎執行、`DP_SCHEDULE_LOG` 記錄執行歷程，job handler 由 DM 提供〔需要業務資料時反向 import DM service〕）：計算統計母體（全部已發布文件，不含訓練教材）之 KPI，產生並寄送 ① **KPI 週報**（Email 予**所有具 DM_ADMIN 角色者**，內文摘要〔含閱讀率**最低前 5 份**〕 + **儀表板連結**；明細 CSV 由 DM06 匯出、不走附件）② **未讀提醒**（Email 予未看之閱覽者，一人一信、彙整其未看文件）
- **FR-004a**: `SCHDM001` 之每週執行時間（星期＋時間）MUST 可由管理者調整，預設 `週一,10:00`（**台灣時間**，見 [`dp/spec_us11.md`](../dp/spec_us11.md) FR-DP-US11-07b）；**KPI 週報與未讀提醒共用同一時間**、同批執行
  > **SA 裁示（2026-09-02，Q1=A）**：交付前盤點確認平台排程引擎僅依 `DP_SCHEDULE.CRON_EXPR` 觸發（`CronTrigger.from_crontab`），而 `DP_PARAM.DM_WEEKLY_SCHED_DAY_TIME`（`星期,HH:MM`，預設 `週一,10:00`）目前無任何程式讀取、與引擎無同步橋接。裁定**執行時間之單一事實來源＝`DP_SCHEDULE.CRON_EXPR`**，由管理者於平台既有 DP 排程後台直接編輯（即時生效）；`DM_WEEKLY_SCHED_DAY_TIME` 保留為**預設值紀錄、不參與實際排程決策**。原「於通知範本設定頁編輯時間並反寫 CRON」視為**未來平台增強**、不在 US13 範圍。US13 以 migration 將 `SCHDM001` 之 `CRON_EXPR` 設為 `0 10 * * 1`（對齊預設）並接上 handler、啟用。
  >
  > **更正（#332，2026-09-17）**：`0 10 * * 1` 實際觸發於**週二**——APScheduler 的
  > `from_crontab` 以**週一為 0**，不做標準 crontab（週日為 0）的轉換。本裁示欄位保留
  > 原文以存證，實際值已由 `c8b4e2f1d97a` 更正為 `0 10 * * 0`（週一 10:00）。
  >
  > **⚠️ 2026-10-05（#517）更正本行的時區標註**：原文寫「週一 10:00 **UTC**」。那是 #332 修
  > day-of-week 時順手描述當下實際值的括號，**不是時區裁示**——全鏈（本 FR、ET `spec_us14`、
  > `DM_WEEKLY_SCHED_DAY_TIME` 種子值）都只寫「週一 10:00」而無時區。#517 裁定排程一律以
  > **台灣時間**解讀（見 [`dp/spec_us11.md`](../dp/spec_us11.md) FR-DP-US11-07b），故 `0 10 * * 0`

  > 另本裁示「`DM_WEEKLY_SCHED_DAY_TIME` 保留為預設值紀錄」那一半已於 #332 推翻，該參數已移除。
  >
  > **⚠️ 2026-09-17（#332）推翻上述「保留」那一半**：`DM_WEEKLY_SCHED_DAY_TIME` 已由 migration `a3f7c21e58d9` 移除。「單一事實來源＝`CRON_EXPR`」的部分不變、且更徹底。
  >
  > 推翻的三個理由：(1)「預設值紀錄」**沒有任何讀者**——不被引擎讀、不被 handler 讀、也不在任何產生流程中被讀，真正的預設值寫在 `9eb4dd6e496b` 的 `_SCHDM001_CRON`；(2)「不參與決策」是寫在規格裡的，**管理者在 DP 後台面對的仍是一個改得動而無效的輸入框**；(3) ET 已於 #325 移除 `ET_WEEKLY_STAT_DAY_TIME`，兩模組對同一問題給出不同答案會讓後人無從判斷哪個是對的。

  > 「於通知範本設定頁編輯時間並反寫 CRON」這個未來增強**一併作廢**——它會重新製造兩個事實來源。要改時點就到「排程管理」改 `CRON_EXPR`。
- **FR-005**: 未讀提醒 MUST **涵蓋統計母體之全部文件**（不含訓練教材，見 FR-002；不設文件層個別開關）；是否寄送由管理者於通知範本「未讀提醒」**啟用 / 停用**統一控制（停用則整批不寄，KPI 統計 / DM06 儀表板 / KPI 週報不受影響）
- **FR-006**: 排程寄信 MUST 呼叫平台唯一發信服務（傳 `template_code`）、由 outbox `DP_EMAIL_LOG` 背景批次非同步寄送（沿用 [spec_us6.md](spec_us6.md) FR-008 之集中 outbox 機制）；平台發信為「呼叫方備妥 `params` → outbox 非同步寄送」、**不做寄送時動態組信**，故 **`SCHDM001` 之 `run` 於執行當下由 DM 逐位收件人算好內容**（未讀提醒逐人算未看清單、KPI 週報算統計摘要）後**逐一以固定 `params` 呼叫平台發信服務 enqueue**。「KPI 週報」「未讀提醒」為 `DP_NOTIFY_TEMPLATE`（`MODULE=DM`）之內建事件（CHANNEL=EMAIL_ONLY），可由管理者於平台 DP 系統管理後台「通知範本」（按模組過濾，見 [spec_us1.md](spec_us1.md)）啟用 / 停用、編輯主旨內文
- **FR-007**: outbox 寄送之**韌性**（最大重試、重試間隔、批次限流）由**平台發信引擎**負責，調校參數屬**平台級 `MAIL` 參數組**（`RETRY_MAX` 預設 5、`RATE_PER_MIN` 預設 60/分、`RETRY_INTERVAL_MIN` 預設 2 分），於平台 DP 系統管理後台維護（平台級參數為共用項，ET / DM 管理者皆可維護）；**FAILED 比率不做系統內告警，由 IT 監控機制負責**（2026-07-09 對齊平台，原失敗告警參數作廢）；DM 不自持此類發信引擎參數（詳見 research §9d 註記與平台 DP 規格）
